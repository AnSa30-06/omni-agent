# Development

## Running from source

```bash
git clone https://github.com/AnSa30-06/omni-agent.git
cd omni-agent
npm install
node scripts/bootstrap.mjs        # gateway + harness into ./runtime
node bin/omni-agent.mjs setup
```

Node 22+. No build step: everything is plain ESM JavaScript, deliberately. An installer that
has to compile TypeScript on a user's machine is an installer with one more way to fail, and
there is no `dist/` to drift out of sync with `src/`.

## Layout

```
bin/omni-agent.mjs          launcher and CLI
plugin/index.mjs            the 8 tools, exposed to OpenCode
src/
  config.mjs                settings (never secrets)
  gateway/
    locate.mjs              find omniroute / opencode on disk
    client.mjs              /v1 inference vs /api management, kept apart
    supervisor.mjs          spawn the isolated gateway, per-install secrets
    provision.mjs           mint the gateway credential
  routing/
    catalog.mjs             live /v1/models + local metadata + pricing
    select.mjs              presets, intent x preset, scoring
    execute.mjs             the only place that calls a model; fallback lives here
  tools/
    search.mjs  web.mjs  browser.mjs  documents.mjs
  providers/usage-adapters.mjs
  usage/telemetry.mjs  usage/dashboard.mjs
  setup/wizard.mjs  setup/doctor.mjs  setup/opencode-config.mjs
  util/paths.mjs  secrets.mjs  redact.mjs  http.mjs  log.mjs  diagnostics.mjs
config/                     opencode template, permissions, model metadata
skills/                     generated by scripts/write-skills.mjs
installer/                  Inno Setup script, launcher shims, portable scripts
```

## Tests

```bash
npm test                  # unit: 25 tests, no network, ~1 s
npm run test:integration  # live network + real browser, ~30 s
npm run test:browser      # browser only
npm run test:e2e          # full research workload through the real agent
```

Unit tests use a synthetic catalogue so routing is testable without a gateway. Integration
tests hit the real internet on purpose — the point is that providers still behave the way
the code assumes.

The two most important tests are in `tests/integration/browser.test.mjs`: one asserts a
submit button is **refused** without authorisation and the page did not navigate; the other
asserts the same button **goes through** once authorised and the server received the values.
Those are the only automated proof that the confirmation boundary holds.

## Building

```bash
npm run build:installer   # dist/OmniAgentSetup-<version>.exe   (~46 MB)
npm run build:portable    # dist/OmniAgent-Portable-<version>.zip (~76 MB)
```

`build:installer` downloads the pinned Node runtime, **verifies it against nodejs.org's own
published SHASUMS256**, stages the app, and runs Inno Setup. `build:portable` zips the same
staging directory, so run the installer build first.

Needs Inno Setup 6:

```bash
winget install --id JRSoftware.InnoSetup
```

`ISCC_PATH` overrides the compiler location.

## Adding a tool

Tools live in `plugin/index.mjs`. **Adding one is a real cost** — every description is spent
from the model's context on every turn, so prefer an `action` argument on an existing tool
over a ninth entry.

```js
my_tool: tool({
  description: "What it does AND when to use it. Both halves matter.",
  args: { thing: z.string().describe("...") },
  async execute(args, ctx) {
    return { title: "short", output: "the result", metadata: {} };
  },
}),
```

Truncate large output with the shared `clip()` helper so the model can see it got a prefix.

## Adding a skill

Edit `SKILLS` in `scripts/write-skills.mjs`, then:

```bash
node scripts/write-skills.mjs
node bin/omni-agent.mjs setup --non-interactive   # reinstall into the config dir
```

The `description` decides whether a skill ever fires — write what it does *and* when to use
it, front-loading the words a user would actually say.

## Adding a provider

See [providers.md](providers.md). The contract is three states — `live`, `unavailable` with
a reason and remedy, `error` — and **no fourth state that fabricates a number**.

## Working on routing

```bash
node bin/omni-agent.mjs route     # what each task gets, and why
node bin/omni-agent.mjs models    # what the gateway serves right now
```

`tests/unit/routing.test.mjs` runs against a synthetic catalogue. If you change the
intent × preset table, the test asserting all five presets differ for `task=code` is the one
that catches the regression that matters.

## House rules

Three, all learned the hard way in this codebase:

**Never state a number a provider did not give you.** Not a quota, not a balance, not a
throughput, not a price. `unavailable` with a reason is a correct answer. See the
exact-match pricing logic in `catalog.mjs` for what this costs in practice.

**A check that passes on a broken system is worse than no check.** Every `doctor` row is a
live probe. The health check caught a rate-limited pool only because it makes a real model
request.

**Measure, then claim.** `_snapshotForAI` was assumed present and is not.
`ariaSnapshot({ref:true})` was assumed to emit refs and does not. The OmniRoute plugin was
assumed to read `XDG_DATA_HOME` and does not. Every one of those was found by running it.

## Pre-push gate

```bash
npm test
npm run test:integration
npm run scan:secrets
npm run build:installer
```

`scan:secrets` runs over everything git tracks, with its own detectors deliberately
independent of `src/util/redact.mjs`, so a bug in redaction cannot also blind the scanner.
It also fails if `credentials.dat`, `config.json`, `auth.json` or `.env` are tracked at all.
